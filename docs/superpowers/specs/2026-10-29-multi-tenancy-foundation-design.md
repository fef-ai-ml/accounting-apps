# Multi-tenancy foundation: Keycloak Organizations + `tenant_id` + Postgres RLS

Date: 2026-10-29
Status: implemented on feat/multi-tenancy

## Goal

Make the platform able to serve several customer companies (tenants) from one deployment, with each tenant's data
isolated from every other tenant. Company #1 runs as the only tenant at first; adding customer #2 later must not need
any table or query rewrite. This is project 1 of 2: the accounting module
(`2026-10-29-accounting-core-design.md`) is built on top of it.

### Success criteria

- Every tenant-owned row carries `tenant_id`; a user of tenant A can never read, change or detect the existence of
  tenant B's rows, through the API or through a bug in our queries.
- The tenant of a request comes only from the access token, never from a header, URL or request body.
- A tenant can be suspended without touching Keycloak; its users then get no permissions within 60 seconds.
- Existing task rows on the home-lab database end up in the `demo` tenant after the migration.
- `./mvnw verify` proves isolation with two tenants, including at the database level with Hibernate bypassed.

### Decisions taken during design

| Topic | Decision |
|---|---|
| Isolation model | Shared tables + `tenant_id` column + Postgres Row-Level Security (RLS). Not schema or database per tenant |
| Tenant identity | Keycloak Organizations in the existing `zk-spring` realm; one organization per tenant |
| Tenant id | The Keycloak organization id (UUID), stored as `tenant_id UUID`. Never generated by us |
| Token claim | Keycloak's default `organization` claim: a list of organization **aliases**, e.g. `["demo"]` |
| Alias → id | `iam` translates the alias to the UUID through a new `TenantDirectory` interface |
| Users per tenant | One user belongs to exactly one tenant. Zero or several organizations in the token means "no tenant" |
| Roles | Unchanged: Keycloak realm roles + the global `iam.role_permission` map. A role applies inside the user's tenant |
| Suspension | `iam.tenant.status` (`ACTIVE` / `SUSPENDED`); a non-active tenant gets no permissions |
| Onboarding | Manual two-step admin procedure (Keycloak organization, then `iam.tenant` row). No self-service yet |

Facts verified on 2026-10-29 against a throwaway Keycloak 26.8.1 container:

- Realm import keeps a fixed organization `id` given in the realm file.
- The default `organization` claim is a list of aliases. The mapper's "add organization id" option yields
  `{"demo": {"id": "…"}}`, but the realm file can only set it by declaring `clientScopes`, and declaring any
  `clientScopes` makes Keycloak skip all built-in scopes: tokens then lose `sub` and `preferred_username`. Therefore
  we use the default alias claim.
- An organization's alias cannot be changed after creation (`"Cannot change the alias"`), so it is a stable lookup
  key. The mapper only runs when the client has the `organization` client scope.

The alias is not used as `tenant_id` itself: if an organization were deleted and a new one created with the same
alias, the new customer would inherit the old customer's rows. Organization UUIDs are never reused.

## Architecture

```
Keycloak realm zk-spring (organizationsEnabled)
 ├─ organization "demo" (id 7f3a0c4e-1b2d-4e5f-8a9b-0c1d2e3f4a5b): admin, editor, viewer
 └─ organization "acme" (id b2c4e6a8-0d1f-4a3b-9c5d-7e8f9a0b1c2d): acme-admin
        │  access token: "organization": ["demo"]
        ▼
backend/security   KeycloakTenant.alias(jwt) → Optional<String>   (exactly one entry, else empty)
                   TenantDirectory.tenantIdOf(alias) → Optional<UUID>   (interface; iam implements it)
        │
        ├─ PermissionResolver (iam): no tenant or tenant not ACTIVE → no permissions → 403 before any data access
        │
        └─ backend/tenancy
             CurrentTenantIdentifierResolver: tenant UUID of the current JWT, else the "root" marker
             MultiTenantConnectionProvider:   set_config('app.tenant_id', <uuid>) on checkout, reset on release
                 │
                 ▼
             Hibernate @TenantId filter (app side)  +  Postgres RLS policy (database side)
```

Three independent barriers stop a request without an active tenant: no permissions (`@PreAuthorize` 403), no
Hibernate tenant filter value (root marker sees no tenant entity rows that RLS would allow), and no `app.tenant_id` on
the connection (RLS shows 0 rows and rejects writes).

## Backend

### `backend/security` (changed)

- `KeycloakTenant`: `static Optional<String> alias(Jwt jwt)`. Returns the single alias when the `organization` claim
  is a list (or JSON object, whose keys are aliases) with exactly one entry; empty for a missing, empty, multi-entry or
  malformed claim. Same style as `KeycloakRoles`.
- `TenantDirectory` interface: `Optional<UUID> tenantIdOf(String alias)`. When no bean exists, `SecurityModule`
  registers a fallback (`TenantDirectory.none()`) that returns empty for every alias and logs a warning once (fail
  closed, like `PermissionResolver.denyAll()`).
- `KeycloakJwtAuthenticationConverter` resolves the tenant once and returns a `KeycloakAuthentication` carrying it.
- Convenience: `static Optional<UUID> tenantId(Jwt jwt, TenantDirectory directory)` combining the two.

### `backend/tenancy` (new module)

Entered through `TenancyModule` (`@Configuration`, `@Import(SecurityModule.class)`), imported by every module that
owns tenant data. It depends on Hibernate, which is why it is not part of `security` or `common`.

- `JwtTenantIdentifierResolver implements CurrentTenantIdentifierResolver<UUID>`: reads the tenant
  from the `KeycloakAuthentication` in `SecurityContextHolder` and returns it (no lookup here: a `TenantDirectory`
  query inside the resolver would recurse into Hibernate). Without an
  authenticated JWT or a resolvable tenant it returns the root marker (a constant all-zero UUID) and `isRoot` answers
  true for it, so Hibernate does not filter; global tables (`iam.*`) are readable and tenant tables are protected by
  RLS (no `app.tenant_id` is set for root).
- `RlsConnectionProvider implements MultiTenantConnectionProvider<UUID>`: wraps the Spring `DataSource`. On
  `getConnection(tenant)` it runs `select set_config('app.tenant_id', ?, false)` for a real tenant and `''` for
  root; on `releaseConnection` it runs `select set_config('app.tenant_id', '', false)`. When the connection is not in
  autocommit, the setting is committed on its own so a later rollback cannot undo it. If the reset fails, the
  connection is aborted (closed physically) and never returned to the pool.
- A `HibernatePropertiesCustomizer` registers both with Hibernate.
- The exact Hibernate 7 wiring (provider + `@TenantId` discriminator together, `isRoot`) is proven by the first task
  of the implementation plan with a failing test before the module is built on.

Background jobs (none exist yet) must set the tenant explicitly; a job without one runs as root and sees no tenant
data. This rule goes into CLAUDE.md.

### `backend/iam` (changed)

- Migration `V20261030_1__create_tenant_table.sql`:
  `iam.tenant(id UUID PRIMARY KEY, alias VARCHAR(100) NOT NULL UNIQUE, name VARCHAR(200) NOT NULL,
  status VARCHAR(20) NOT NULL CHECK (status IN ('ACTIVE','SUSPENDED')), created_at TIMESTAMPTZ NOT NULL DEFAULT now())`,
  seeded with `demo` (`7f3a0c4e-1b2d-4e5f-8a9b-0c1d2e3f4a5b`, `ACTIVE`) and `acme`
  (`b2c4e6a8-0d1f-4a3b-9c5d-7e8f9a0b1c2d`, `ACTIVE`), the same ids as in the realm file. Grants `SELECT` on all `iam` tables to `app_runtime`.
- `Tenant` entity + `TenantRepository` (Spring Data JPA, no `@TenantId`: the table is global).
- `DbTenantDirectory implements TenantDirectory`: Caffeine cache, 60 s, alias → `(id, status)`. Only `ACTIVE`
  tenants resolve; a suspended or unknown alias resolves to empty, so a suspended tenant also has no Hibernate tenant
  and no RLS tenant.
- `DbPermissionResolver.permissionsFor(jwt)`: returns no permissions when the token has no resolvable active tenant;
  otherwise unchanged.
- `/api/iam/me` adds `tenant`: `{id, alias, name, status}` when the token's alias is known (including `SUSPENDED`, so
  the UI can explain), else `null`. `/api/iam/roles` unchanged.

### `backend/task` (changed)

- `Task` gains `@TenantId @Column(name = "tenant_id", nullable = false, updatable = false) private UUID tenantId;`.
- Migration `V20261030_2__add_task_tenant.sql`: add nullable `tenant_id`, backfill every row with the `demo` UUID, set
  `NOT NULL`, index `(tenant_id)`, `ENABLE ROW LEVEL SECURITY`, policy `tenant_isolation` with both `USING` and
  `WITH CHECK (tenant_id = nullif(current_setting('app.tenant_id', true), '')::uuid)` (after the reset the setting is `''`, which does not cast to uuid), grants
  `SELECT, INSERT, UPDATE, DELETE` on the table and `USAGE` on schema and sequence to `app_runtime`.
- `TaskModule` imports `TenancyModule`. Fetching another tenant's id yields 404 through the existing
  `TaskNotFoundException` (the row is filtered, not forbidden), so existence is not revealed.

### `backend/app` (changed)

- Runtime datasource: `spring.datasource.username=${DB_RUNTIME_USER:app_runtime}`,
  `password=${DB_RUNTIME_PASSWORD:app_runtime}`.
- Flyway as owner: `spring.flyway.user=${DB_USER:app}`, `spring.flyway.password=${DB_PASSWORD:app}`.

### Database roles

| Role | Used by | Rights |
|---|---|---|
| `app` (existing owner, superuser in dev) | Flyway only | DDL and seeds; bypasses RLS, which is acceptable for migrations |
| `app_runtime` (new) | The running API | `LOGIN`, `NOSUPERUSER`, `NOBYPASSRLS`, owns nothing; only the grants each module's migrations give it |

`app_runtime` is created outside Flyway because roles are cluster-wide and carry a password:
`infra/postgres/init/02-app-runtime.sql` for fresh volumes (dev password `app_runtime`) and a README step for existing
volumes. It must exist before the new migrations run, since they grant to it. Each module grants only on its own
schema, keeping the module-owns-its-schema rule.

## Frontend

- `frontend/shell` client registration `keycloak`: scope `openid,profile,email,organization`.
- `MeDto` gains `tenant` (`TenantDto` with JavaBean getters). `CurrentUser.getTenantName()`.
- Shell header shows the tenant name next to the user. When `tenant` is null or not `ACTIVE`, the shell shows
  "Your organization has no access to this application" instead of the module list (the user is still logged in and
  can log out).

## Infrastructure

### `infra/keycloak/zk-spring-realm.json`

- `"organizationsEnabled": true`.
- Organizations `demo` (id `7f3a0c4e-1b2d-4e5f-8a9b-0c1d2e3f4a5b`, domain `demo.example`, members admin, editor,
  viewer) and `acme` (id `b2c4e6a8-0d1f-4a3b-9c5d-7e8f9a0b1c2d`, domain `acme.example`, member `acme-admin` with
  realm roles `ADMIN` and `default-roles-zk-spring`, password `acme-admin`).
- Client `zk-shell`: `organization` added to `defaultClientScopes`. No `clientScopes` array is declared (see verified
  facts).
- Keycloak skips importing a realm that already exists, and organizations created in the console get random ids that
  would not match the migration's seed. The README upgrade step for an existing setup is therefore: delete the
  `zk-spring` realm in the admin console, then rebuild and restart the Keycloak container so it imports the new realm
  file. The realm holds only demo data; manual changes to it are lost, which the README states.

### `infra/postgres/init/02-app-runtime.sql`

`CREATE ROLE app_runtime LOGIN PASSWORD 'app_runtime' NOSUPERUSER NOBYPASSRLS;` plus `GRANT CONNECT ON DATABASE app`.

## Error handling

| Situation | Result |
|---|---|
| Token without organization, or with several | `/api/iam/me` returns `tenant: null`; every data API 403 |
| Tenant `SUSPENDED` or not in `iam.tenant` | Same; `me` shows the status when the alias is known |
| Tenant A requests tenant B's row id | 404, as if it did not exist |
| Reset of `app.tenant_id` fails on release | Connection aborted, never reused |
| `organization` scope missing on the client | Every user has no tenant; visible in `me` (CLAUDE.md gotcha) |

## Testing

- `KeycloakTenantTests`: list with one alias, JSON object with one key, empty, two entries, missing, wrong type.
- `TaskApiTests` with two tenants (Testcontainers): A creates; B lists nothing; B `GET`/`PUT`/`DELETE` on A's id → 404;
  token without organization → 403. Sets a `KeycloakAuthentication` per request instead of stubbing `TenantDirectory`, so the module still boots alone.
- RLS without Hibernate (`TenancyTests`, `TaskApiTests.rowLevelSecurityAloneHidesOtherTenantsTasks`; native SQL as
  `app_runtime`): with tenant A set, B's rows count 0; with
  nothing set, all counts 0; inserting a row with B's `tenant_id` while A is set is rejected. First asserts that the
  connected role is not superuser, owns no table and has no `BYPASSRLS`, otherwise the other assertions prove nothing.
- Pool-leak test: pool size 1; a request as A followed by a request without tenant on the same connection sees no rows.
- `iam`: suspended and unknown aliases → no permissions; `me` shows tenant and status; directory cache behaviour.
- `TokenToPermissionsTests`: real RS256 tokens now carry `organization`.
- Tests run Flyway as the container's superuser and the application as `app_runtime` (created by a test init script),
  so `@ServiceConnection` is replaced by explicit properties where both users are needed.
- Frontend: context tests; the client registration requests the `organization` scope.
- README manual checklist adds: `acme-admin` sees none of demo's tasks; suspending `acme` shows "no access" within
  60 s; existing home-lab tasks appear under `demo`; a Keycloak user outside any organization sees "no access".
